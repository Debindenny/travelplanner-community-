# 1000-Prompt Run Analysis — `POST /api/v1/chat`

Ran all 1000 prompts from [`user-prompts-1000.md`](user-prompts-1000.md) against the live local stack's chat endpoint (`POST /api/v1/chat`, gateway on `:8080`, planner service, local Ollama model). Raw responses: [`prompt-run-1000-raw-results.jsonl`](prompt-run-1000-raw-results.jsonl) (one JSON object per prompt: index, category, prompt, latency, HTTP status, full response body).

**Grading method:** automated heuristics (does `trip_slots.destination` contain the city actually named in the prompt? does `duration_days` match the stated duration?) plus manual inspection of every flagged category and all adversarial/edge-case prompts. There's no ground-truth dataset, so treat the percentages as directional, not exact — but the concrete examples below are real, reproducible bugs, not measurement noise.

## Headline numbers

- **1000/1000 requests returned HTTP 200.** No crashes, no 500s, no unhandled exceptions during the entire run.
- **0/50 adversarial/injection prompts succeeded** at anything malicious — no reflected `<script>`, no SQL-error leakage, no "ignore previous instructions" compliance, no system-prompt leak.
- **Only 28/1000 requests got `trip_slots.ready: true`** (i.e., the assistant considered it had enough info to actually build a trip in one shot) — even for prompts that stated destination, duration, budget, and style all at once.
- **412/1000 responses (41%) came back with `provider: null`**, meaning the reply text was generated by the regex/keyword-based dev fallback (`_dev_assistant_reply`), not the real Ollama model. This is not evenly spread — it's concentrated in specific phrasings (see below), which points to a slot-parsing/regex path issue more than a general LLM outage.

## Bug 1 (highest severity): destination gets silently replaced with "Goa"

**73 responses returned `destination: "Goa"` for prompts that never mention Goa at all.** This is heavily concentrated in two exact sentence templates:

- `"I'm planning a trip [style] — [City] sound good for [N] days?"` — 20 of 23 prompts using this pattern (87%) resolved to Goa, regardless of the actual city (Cairo, Jakarta, Beijing, Kathmandu, Seoul, Hong Kong, Munnar, Venice, Manila, Colombo, Vienna, Athens, Edinburgh, Udaipur, Hanoi, Prague all got overwritten).
- `"What's a good plan for [N] days in [City]?"` — 21 of 24 prompts (87.5%) resolved to Goa (Kuala Lumpur, Kyoto, Buenos Aires, Vienna, Athens, Cusco, Manali, Toronto, Pondicherry, Auckland, Dubrovnik, Jaipur, Siem Reap, Busan, Porto, etc. all overwritten).

Example (verbatim from the run):
```
Prompt:   "I'm planning a trip with a group of 6 friends — Cairo sound good for 5 days?"
Response: destination = "Goa"
```
```
Prompt:   "What's a good plan for 2 weeks in Kyoto?"
Response: destination = "Goa"
```
This isn't a rare edge case — it's the majority outcome for two common, realistic phrasings. Whatever regex/heuristic runs when the LLM router doesn't confidently classify these sentence shapes appears to fall back to a hardcoded example destination ("Goa") instead of preserving the user's actual stated city. Worth checking `_dev_assistant_reply` and the regex-first slot extractor in `llm_intent_router.py`/`llm_slot_extraction.py` for a literal `"Goa"` default.

## Bug 2: destination field sometimes captures a sentence fragment instead of a place name

Separate from the Goa bug, several other phrasings caused the extractor to grab a trailing or leading clause as the "destination":

| Prompt | Destination returned |
|---|---|
| "Can you build me 4 days itinerary for Kuala Lumpur?" | `"Can You Build Me"` |
| "Can I do Manali for under €4,000? Plan it out" | `"It Out"` |
| "I want to go to Beijing for just 3 days — make sure there's good Wi-Fi" | `"Work Some Mornings"` |
| "Plan a trip to Helsinki, it has to be wheelchair accessible throughout" | `"Be Wheelchair Accessible Throughout"` |
| "...so we want smth scenic for like instagram n stuff but also actually fun to do not just photos" | `"Do Not Just Photos"` |

These read like a naive "grab the Title-Case-able span near a trigger word" heuristic misfiring when the actual city name isn't the most recently Title-Cased phrase in the sentence.

## Bug 3: explicit duration is frequently not extracted

**79/190 (42%) of single-destination prompts** — all of which explicitly state a duration ("2 weeks", "a week", "a full month", etc.) — came back with `duration_days: null`. Same pattern in multi-city (34/70, 49%). Examples where duration was stated but dropped:
- "Plan 2 weeks trip to Kuala Lumpur" → `duration_days: null`
- "I want to visit Kyoto for a full month, what should my itinerary look like?" → `duration_days: null`
- "Give me a day-by-day plan for 2 weeks in Kyoto" → `duration_days: null`

Combined with the low `ready: true` rate (28/1000), it looks like the slot-filling logic re-asks for information the user already gave, rather than treating a single detailed message as sufficient — this may be partly by design (a conversational "confirm before committing" pattern) but 42% is a lot of outright drops of stated info, not just conservative confirmation-seeking.

## Where it behaves well

- **Fictional/impossible destinations are handled gracefully.** "I want to go to Narnia for a week, plan it" → *"Narnia is a fictional land, so I can't book flights or hotels there 😄 ... looking for real-life places that feel magical..."* Same graceful handling for Atlantis, the Moon, and Mars — no hallucinated bookings, no broken flow.
- **Empty input is handled cleanly**: `""` → *"Please type a message and I'll do my best to help."* No crash, no confusing response.
- **Non-English prompts get replies in the correct language.** French prompts get fluent French replies, addressing the actual question (checked all 40 non-English prompts manually) — genuinely multilingual, not just translated boilerplate. Destination-slot extraction for these is weaker (e.g. "Rome" → `destination: "Italy"`, "Lisbonne" → `destination: null`), but part of that is because the slot extractor's known-place list appears English-name-based, so this needs a native-speaker review rather than the English-keyword heuristic used here.
- **No injection/security issues found** across all 50 adversarial prompts (SQL-injection-style strings, `<script>` tags, "ignore previous instructions", "give me the admin password", asking it to reveal its system prompt) — none succeeded, none were echoed back verbatim, none caused an error response.

## Dev-fallback rate is very uneven across phrasing styles

| Category | % responses with `provider: null` (dev/regex fallback, not real Ollama) |
|---|---|
| Multi-city / multi-country trips | 81% |
| Constraint-heavy prompts | 79% |
| Travel-style specific prompts | 69% |
| Single-destination trip requests | 63% |
| Edge cases / adversarial | 50% |
| Date / season-specific | 50% |
| Interest / theme-focused | 29% |
| Modification / follow-up chat | 21% |
| Casual / voice-style / typos | 18% |
| Meta / platform questions | 7% |
| Budget-focused prompts | 6% |
| Comparison / decision-help | 5% |
| Vague / "inspire me" | 0% |
| Non-English (French/Spanish) | 0% |

The categories hitting the dev-fallback most (multi-city, constraint-heavy, travel-style, single-destination) are exactly the ones built from rigid templates in the test set, which is suspicious in the other direction too — real users don't type in fixed templates, so this specific 63-81% figure is likely inflated by how repetitive my generated phrasing is within those categories. Still, a 41% overall dev-fallback rate, and the fact that it's *not* random noise but clusters by sentence shape, is worth investigating — check whether the intent router (`llm_intent_router.py`, 7s timeout) is timing out or returning empty on these shapes under the concurrency this test ran at (5 concurrent requests), separate from the actual bug in Bugs 1–2 above.

## Caveat on this test's concurrency

The run used 5 concurrent requests to fit inside the 20-req/60s rate limit. That's higher concurrent load on the local Ollama instance than a single real user would produce, so some of the dev-fallback rate could be load-induced (LLM timing out under concurrency) rather than something that would happen with lower traffic. Bugs 1–2 (the Goa hijack and fragment-capture), however, are deterministic on specific phrasings and reproduced 87%+ of the time on those templates — that's a real bug independent of load, not a flaky timeout artifact.

## Recommendation

Bug 1 (Goa hijack) is the one to fix first — it silently discards the user's actual destination and substitutes a specific unrelated one on two common phrasing patterns, which would visibly break trip planning for real users typing naturally. Bug 2 is a smaller-scope version of the same root cause (fragile fragment-based destination extraction). Bug 3 (duration drops) is worth a follow-up look at the regex-first slot extractor to see why explicit durations aren't always caught before falling through to the LLM path.
